# Reduce Novice Decision Load with Safe Defaults and Explicit Optionality

## Pattern Rule
**IF** an adventure module is meant to be run by a novice operator who cannot yet distinguish essential preparation from optional customization
**THEN** provide one complete safe default for setup and first use, label optional or customizable choices explicitly, and postpone open-ended invention until the operator has already seen the module work
**ELSE** expose more design freedom up front when the intended operator already knows which decisions are load-bearing

## Do
- State the minimum entry requirements and preparation sequence in operational order: what must be read, what must be prepared, what may be prepared later, and what can be used exactly as written.
- Supply a usable default whenever omission would otherwise force the novice to invent material before first play, such as a starting situation, initial information, ready roles, a route into the scenario, or a basic procedure for recurring situations.
- Distinguish required, recommended, optional, and extension material in the prose instead of presenting every suggestion with equal weight.
- Put common variations behind bounded choices: explain what changes if the group, available preparation time, or intended scope differs, without making the novice redesign the whole scenario.
- Give permission to personalize only after the baseline is clear enough that the operator knows what the change is modifying.
- Make the first runnable state smaller than the full design space; later sections can widen choice once the operator has a concrete model in hand.

## Don't
- Advertise flexibility by leaving basic setup incomplete and expecting a beginner to fill the gaps before use.
- Front-load a long menu of equivalent options when the novice still needs to know which one is the normal starting point.
- Hide a required preparation step in a later keyed location or appendix that the operator is unlikely to read before play.
- Treat optional enrichment as mandatory preparation simply because it would improve visualization or polish.
- Give customization advice without preserving the scenario functions that the customized element must still perform.
- Remove all judgment from the operator; a safe default should reduce initial decision load, not turn live operation into verbatim execution.

## Checklist
- A novice can identify the minimum preparation needed for the first session without comparing several distant sections.
- The module supplies a complete runnable default for every setup decision that would otherwise block first use.
- Optional preparation and personalization are visibly marked as optional rather than implied requirements.
- At least one common deviation has bounded guidance instead of requiring wholesale redesign.
- The operator reaches a live decision point before being asked to invent major new scenario content.
- Following the defaults still leaves meaningful room for player choice and operator judgment during play.

## Notes
Introductory writing fails when it confuses freedom with absence of support. A veteran can look at an incomplete scenario and infer what needs to be added; a novice may not yet know which missing decisions are structural and which are merely decorative. Safe defaults provide a complete first path through the work while explicit optionality shows where authorship can later expand.

The useful progression is not "explain every possibility, then begin." It is "make the first use possible, identify what was optional, then widen the operator's control." This lets the module teach by successful operation rather than making successful operation the reward for already understanding the craft.
